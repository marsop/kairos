# AI Agent Guidelines

Welcome to the Kairos codebase! This file contains important guidelines and context for AI agents working on this project.

## General
* When generating dates for documentation (like `CHANGELOG.md`), use the actual system output (e.g., via `date +%Y-%m-%d`), even if it outputs a seemingly hallucinated future date (e.g., 2026) due to the specific sandbox configuration. It is technically correct for the environment context.
* The application uses `Nerdbank.GitVersioning` with `version.json` at the repository root. When cutting a release, the new `CHANGELOG.md` version tag is derived from the current `version.json` value (e.g., '1.8' becomes '1.8.0'). Replace `## [Unreleased]` with this new version and date, add a new empty `## [Unreleased]` section at the top, and then increment `version.json` (e.g., to '1.9') for the next cycle.
* When updating CHANGELOG.md, adhere strictly to 'Keep a Changelog' formatting conventions, ensuring there is only one of each category heading (e.g., `### Added`, `### Changed`, `### Fixed`) per version block.
* Always delete any temporal files and logs that you have used preparing the PR as long as they are no longer required by the application.
* Always remember to update the CHANGELOG.md after changes, bugfixes and user-facing features. If in doubt, ask the user whether something should be included in CHANGELOG or not. Do not automatically increase the version unless when explicitly asked to do so.
* When using the `run_in_bash_session` tool, every invocation starts from the repository root directory. Directory changes (e.g., `cd`) do not persist across separate tool calls.
* The project treats compiler warnings as errors. Use `#pragma warning disable` to suppress warnings on intentionally unused members in test stubs to prevent build failures.
* When starting the local development server for frontend verification (e.g., `dotnet run` in `src/Kairos.Web`), the application typically listens on port 5111 (`http://localhost:5111`).
* When creating execution plans (e.g., for `request_plan_review` or `set_plan`), you must explicitly include a step to run tests (e.g., `dotnet test`) before the pre-commit step. The pre-commit step itself must use the exact phrasing: 'Complete pre-commit steps to ensure proper testing, verification, review, and reflection are done.'
* When creating execution plans, follow the 'Specificity Rule' for testing steps by providing exact commands (e.g., starting the background server and running `dotnet test Kairos.sln`) rather than generic instructions like 'Run Tests'.
* Workflow Directive: Always enter a deep planning mode before starting work. Actively verify all assumptions and clarify requirements by asking questions using the `request_user_input` and `message_user` tools. Only generate a plan using `set_plan` when you have absolute certainty of expectations. Once the plan is approved, execute autonomously without seeking further confirmation.
* When generating execution plans, strictly adhere to the 'Groundedness Rule' by ensuring all referenced methods, variables, and logic details are explicitly confirmed in the current session's trace (e.g., via `read_file` or `grep`). Do not assume or hallucinate implementation details based on prior knowledge when writing tests or modifying logic.
* Always start tasks in a deep planning mode. Ask clarifying questions using `request_user_input` and `message_user` tools until absolute certainty of the user's requirements is achieved. Only create an execution plan using `set_plan` after all assumptions have been tested and doubts resolved. Once the plan is approved and executed, proceed autonomously without asking for further confirmation unless absolutely necessary.
* When creating execution plans that modify or create files, always include an explicit step to verify the written contents using `read_file` immediately after the file modification.
* The repository contains a .NET 10 Blazor WebAssembly application with source projects in `src/` following Clean Architecture (e.g., Kairos.Web, Kairos.App, Kairos.Core, Kairos.Application, Kairos.Infrastructure) and test projects in `tests/` (e.g., `tests/Kairos.ValidationTest/Kairos.ValidationTest.csproj` using xUnit).
* When creating execution plans (e.g., for `request_plan_review` or `set_plan`), you must explicitly include a step to run tests before the pre-commit step. Follow the 'Specificity Rule' for testing steps by providing exact commands (e.g., starting the background server and running `dotnet test Kairos.sln`) rather than generic instructions like 'Run Tests'. When running tests from the repository root, use `dotnet test Kairos.sln` instead of `dotnet test` alone to prevent MSB1003 errors (missing project/solution file). The pre-commit step itself must use the exact phrasing: 'Complete pre-commit steps to ensure proper testing, verification, review, and reflection are done.'
* To avoid output truncation limits (e.g., 1000 characters) when exploring large source files via the bash shell, use paginated commands like `sed -n '1,50p'` or targeted searches like `grep -A 15` to ensure the complete logic is read and confirmed before generating test cases or plans.
* When planning string replacements across multiple localized files (e.g., `.resx`), you must first read (e.g., via `grep`) the exact current text from *each* target file to adhere to the Groundedness Rule. The plan must then include the exact original and replacement strings for each file to satisfy the Specificity Rule.

## Build & Dependencies
* When running automated tests with `dotnet test`, avoid passing multiple project directory paths in a single command to prevent MSB1008 errors. Execute them individually or target the solution file.
* The solution utilizes Central Package Management (CPM). All NuGet package versions must be managed centrally in a root `Directory.Packages.props` file using `<PackageVersion>` elements, and `.csproj` files should omit the `Version` attribute from `<PackageReference>` items.
* When running tests from the repository root, use `dotnet test Kairos.sln` instead of `dotnet test` alone to prevent MSB1003 errors (missing project/solution file).
* If `dotnet build` or `dotnet test` fails with `Nerdbank.GitVersioning.GitException: Shallow clone lacks the objects required to calculate version height`, resolve it by running `git fetch --unshallow` to retrieve the full commit history.
* The project treats compiler warnings as errors during the build process. Use `#pragma warning disable` (e.g., `#pragma warning disable CS0067`) to suppress warnings on intentionally unused members in test stubs to prevent build failures.

## Blazor & UI
* UI Pattern: When calculating bottom padding for scroll containers (like `.main-content`) to clear fixed bottom navigation bars, always include `env(safe-area-inset-bottom)` to prevent occlusion by iOS/Android home indicators.
* UI Pattern: Information banners or summary cards that display context and prominent metrics (like current activity or budget periods) use the global `.stat-summary-card` class container, combined with `.stat-label` for small descriptive text and `.stat-big-value` for the prominent metrics.
* Standard dialog action buttons across the application should use the global CSS classes `.btn-cancel`, `.btn-save`, and `.btn-delete` defined in `app.css`. Avoid using component-scoped CSS overrides or alternative classes like `.btn-secondary` or `.btn-danger` to maintain a unified design.
* ActivityBudgets are persisted in local storage under the key 'Kairos_budgets' and managed via `StatisticsService` using `IStorageService`. They act as rolling/recurring budgets based on their `BudgetType` (Monthly, Weekly, Daily).
* UI Pattern: Action buttons (like 'edit') on summary cards (e.g., `.stat-summary-card` across components) should be placed as dedicated `<button>` elements positioned in the top right corner using absolute positioning, and should use SVG icons instead of emojis.
* In Blazor components subject to frequent timer-based re-renders, use `@bind:event="oninput"` on `<textarea>` and text inputs to ensure the C# state updates on every keystroke, preventing re-renders from overwriting un-blurred user input and causing focus jumps.
* In Blazor custom dropdowns (using @onfocusout on the container to close), use @onmousedown combined with @onmousedown:preventDefault="true" on dropdown items instead of @onclick. This prevents focus loss race conditions that prematurely close the dropdown before the selection logic can register.
* For performant continuous UI animations in Blazor (like zoom or scroll scaling), avoid C#-driven frame-by-frame loops calling `StateHasChanged()`. Delegate the animation loop to JavaScript (`requestAnimationFrame`) and apply scaling via CSS variables.
* To prevent parent component re-renders (e.g., from timers) from overwriting user input and stealing focus in Blazor edit dialogs (like `EditEventDialog.razor`), guard local state initialization inside `OnParametersSet` by comparing the incoming entity's ID against a locally stored `_lastEntityId`. Ensure `_lastEntityId` is cleared when the entity parameter becomes null to support re-opening the dialog.
* To trigger client-side file downloads in Blazor components, invoke the `kairosFile.downloadText` JS interop function, passing a `FileDownloadRequest` record containing the `FileName`, `Content` (e.g., CSV string), and `ContentType` (e.g., 'text/csv;charset=utf-8').
* In `History.razor`, the timeline chart and its `.chart-container` only render when the view is 'stats' and there are recorded events (`AllEvents.Any()`). When no events exist, an `.empty-state` block is shown using the `NoEvents` or `NoEventsForDate` localized strings.
* When dynamically injecting localized strings into raw HTML or SVG elements using `MarkupString` in Blazor, wrap the `Localizer` call with `System.Net.WebUtility.HtmlEncode` to prevent XSS and markup breakage.
* UI Pattern: Action buttons on Activity cards (contained within `.activity-actions`) should be aligned to the top-right using the `right` CSS modifier class and must be permanently visible, avoiding hover-dependent opacity.
* UI Pattern: Standard inline edit buttons outside of dialogs should use the global `.edit-btn` CSS class with the standard SVG pencil icon, avoiding component-scoped overrides (e.g., `.budget-edit-btn`) to ensure unified hover effects and styling.
* UI Pattern: Item deletion (like deleting History events) should occur via explicit text-based buttons within the item's edit dialog (e.g., using 'btn-delete' class) rather than via inline icon buttons on list items to prevent accidental deletions and maintain a cleaner interface.
* When modifying the UI, always ensure that the design is consistent across the application and avoid having different pages looking wildly different from one another.
* For performance in Blazor components (e.g., `History.razor`), avoid executing heavy data aggregation or chart refresh logic (like `RefreshBudgetTimelineData`) inside high-frequency UI timers (e.g., 1-second ticks). Instead, trigger these updates via state-change event handlers (e.g., `TimeService.OnStateChanged`).
* In Blazor components, use `NavigationManager.NavigateTo("")` rather than `NavigationManager.NavigateTo("/")` when navigating to the application root. Navigating to `"/"` can be interpreted as an external URL in PWA or hybrid environments, causing the app to erroneously open a new browser tab.
* In Blazor components, prefer using `@onchange` instead of `@oninput` for input fields that trigger asynchronous save operations or network requests (e.g., calling fire-and-forget `SaveAsync()`). This prevents rapid concurrent executions, blocked locks, and dropped API calls caused by firing on every keystroke.
* In Blazor components, the standard HTML `autofocus` attribute may fail upon reopening dynamic dialogs. To reliably focus input elements, use an `ElementReference` and programmatically call `FocusAsync()` within `OnAfterRenderAsync`, catching potential exceptions if the element is unexpectedly removed from the DOM before focus completes.
* To avoid closure bugs in Blazor components when passing loop variables to event callbacks (like `@onclick`), assign the iteration variable to a local variable within the loop before using it in the callback.
* Prefer using native HTML `<details>` and `<summary>` elements for implementing collapsible accordion UI sections to reduce visual clutter and save screen space without needing external libraries or additional JavaScript.
* Prefer using standard HTML `title` attributes for implementing simple UI hover tooltips on elements (e.g., buttons, activity cards) to reduce DOM and CSS complexity.
* UI Pattern: Icon-only buttons (like SVG edit or delete icons) should only be used outside dialogs. Inside dialogs, buttons should be text-based (e.g., using localized text like `@Localizer["Delete"]`).
* Standard delete buttons in the application UI (e.g., in dialogs or settings) use the `btn-delete` CSS class, which conventionally applies a red background styling.
* Standard UI input elements (e.g., text, number) across the application use the `edit-input` CSS class. Dropdown selections should use the custom structure (`div.custom-dropdown` with `tabindex="-1"` and `@onfocusout`, containing `button.dropdown-trigger` and `div.dropdown-menu`) instead of native `<select>` elements.
* In the UI, filter sections (such as date or view toggles in History.razor) are standardly wrapped in a `<div class="history-date-filter">` and include a `<label class="history-filter-label">` as a header to maintain consistent layout across views.
* Application (in-app) notifications (to toasts) are rendered by `src/Kairos.App/Components/ToastContainer.razor` and styled using `.toast` related CSS classes in `src/Kairos.App/wwwroot/css/app.css`.
* The main application navigation layout and bottom footer tabs are defined in `src/Kairos.App/Layout/MainLayout.razor`.
* The Budgets/Statistics page serves as the application's root route (`href=""` in navigation) and its UI logic is implemented in `src/Kairos.App/Pages/Statistics/Statistics.razor`.
* The UI for global application settings (such as toggles for general or advanced settings) is centralized in `src/Kairos.App/Pages/Settings.razor`.
* The Activity editing interface (which also houses the activity deletion functionality) is located within `src/Kairos.App/Pages/Activities.razor` as a modal dialog (using `modal-overlay` and `modal-dialog` classes) managed via an `_editingActivityId` state, not an inline `isEditing` state. In `src/Kairos.App/Pages/Activities.razor`, the buttons to edit or interact with individual activities use the CSS class `.activity-action-btn`.
* The reusable UI component for editing an ActivityEvent's details (start time, end time, and comment) is located at `src/Kairos.App/Components/EditEventDialog.razor`.
* Activity Group editing in `Settings.razor` is managed via a modal dialog pattern using `_isEditingGroupModalOpen` and `_editingGroupId`, mirroring the Activity edit dialog implementation.
* The Activity Groups management UI is located in a dedicated settings card (`#settings-card-groups`) within `src/Kairos.App/Pages/Settings.razor`, positioned below the Advanced settings.
* Budget UI elements (like progress bars and item borders) should use the application's overall theme colors defined via CSS variables (e.g., green/positive and red/negative) rather than individual activity colors.
* When implementing drag-and-drop interactions in Blazor components, apply `user-select: none;` to draggable elements via CSS to prevent text highlighting, and consider using a full-screen `.drag-overlay` div with pointer event bindings to reliably catch fast movements.
* The application implements its charts (e.g., the trend line in Statistics.razor) using native inline SVG elements rather than relying on external charting libraries. Graph lines in the application (e.g., in Statistics and History pages) should never fall below 0. Ensure the minimum Y-axis value (the 'floor') is explicitly 0.
* The chart type in the History view (e.g., bar chart vs. line chart) is controlled by the `SettingsService.ChartType` string property (e.g., 'bar', 'line').
* Activity positioning within a group is managed via the `DisplayOrder` integer property, with the highest number appearing last.

## State & Data Management
* When removing columns from Supabase schemas, execute the change by appending an `ALTER TABLE public.[table_name] DROP COLUMN IF EXISTS [column_name];` statement to the corresponding `.sql` files in the `supabase/` directory.
* The application uses `CsvHelper` library for CSV reading and writing logic. Avoid manual string construction or other CSV libraries.
* Supabase C# integration relies on `HttpClient` for REST API calls. When adding or modifying persisted fields, update the schema in `supabase/`, map fields in C# DTOs with `[JsonPropertyName]`, and explicitly append the new column name strictly separated by commas without spaces to the `select` query string.
* The Budgets/Statistics page serves as the application's root route (`href=""` in navigation) and its UI logic is implemented in `src/Kairos.App/Pages/Statistics/Statistics.razor`.
* The number of Activity Groups is stored locally in `SettingsData.ActivityGroupCount`, but is not stored in the remote Supabase `user_settings` table. When synchronizing with Supabase, the local group count must be dynamically inferred and updated from the length of the retrieved `user_activity_groups` to prevent data truncation.
* Global application settings changes can be observed in Blazor components by injecting `ISettingsService` and subscribing to its `OnSettingsChanged` event (e.g., `SettingsService.OnSettingsChanged += StateHasChanged`) during initialization and unsubscribing during disposal.
* When adding new properties to `ISettingsService` or `SettingsService`, you must also update the mock implementation `StubSettingsService` located in `tests/Kairos.ValidationTest/TestDoubles.cs` to prevent compile errors in the test suite.
* When adding new global user settings, update the `public.user_settings` schema in `supabase/user_settings.sql` (using `ALTER TABLE IF NOT EXISTS`), add the property to `ISettingsService`, `SettingsService` (including all mappings in `LoadAsync`, `BuildSyncedSettings`, and `ApplySyncedSettings`), `SettingsData`, and `SyncedSettingsData`, and explicitly update the REST `select` query parameters and data mapping in `SupabaseSettingsStore`.
* ActivityBudgets are persisted in local storage under the key 'Kairos_budgets' and are managed via `StatisticsService` using `IStorageService`. ActivityBudgets are designed as rolling/recurring budgets based on their `BudgetType` (Monthly, Weekly, Daily) rather than absolute start and end dates. An activity can have at most one active budget per type, which maps directly to the UI's `ViewMode` (Day, Week, Month) in the Statistics component.
* The `IStorageService` interface's `GetItemAsync` method returns a `Task<string?>` and is not generic. It must be called as `GetItemAsync(key)`, followed by manual deserialization (e.g., using `JsonSerializer.Deserialize<T>`) when retrieving complex objects.
* The `TimeTrackingService.GetTimelineData` method calculates timeline graphs for the Statistics page and expects absolute `DateTimeOffset` start and end boundaries to properly scope data points and start the running balance at zero.
* Use ILogger when possible for logging; never call console.log directly if ILogger is available in the current context.

## Timeular Tracker
* The physical Timeular tracker maps its active face (1-based index) to the ordered list (by `DisplayOrder`) of the user's activities in the currently active UI activity group (`SettingsService.ActiveActivityGroup`). Faces > 8 are explicitly mapped to -1 to ensure no activity is matched and the current activity is deactivated.
* The application retrieves battery levels from connected Timeular trackers using the standard Web Bluetooth Battery Service (`battery_service` / `0x180F`) and Characteristic (`battery_level` / `0x2A19`) via `timeularInterop.js`, syncing it to `TimeularService.BatteryLevel`.
* When Timeular Bluetooth auto-reconnect fails, falling back to the device picker is the correct and intended behavior. Do not remove or alter this fallback.

## Tutorial & Avatars
* The application's tutorial flow is configured in `src/Kairos.Application/Services/TutorialService.cs`, and all corresponding tutorial steps and translatable text are stored in `src/Kairos.Application/Resources/Strings.resx` alongside localized files (e.g., `.de.resx`, `.es.resx`). The sequence is defined by populating a `_steps` list with `TutorialStep` instances, which map a localized string, a target route, and an `ImageUrl`. The avatar images for these steps are assigned dynamically by cycling through available images based on the step index and the current avatar's `ImageCount`.
* Avatar image assets for different styles (e.g., 'kawaii', 'zarzaparrilla') are stored in `src/Kairos.Web/wwwroot/img/avatars/` and named sequentially (e.g., `tutorial-avatar-1.png`). Each style directory must also contain a `tutorial-avatar.png` file (often a resized version of the first pose) to serve as the dropdown icon. When adding new avatar images, add the file to all style directories, update the `README.txt` files, and increment the `ImageCount` property of the respective `AvatarProfile` to dynamically use them in the tutorial.
